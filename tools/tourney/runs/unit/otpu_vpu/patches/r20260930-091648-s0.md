# otpu_vpu slot r20260930-091648-s0 (killed in its gates when the tournament stopped, 2026-09-30 15:25)

# One lane-level adder in the folding tree, 9-bit converters in the long lanes

Category: area

## Motivation

The OOC build (LANES 8, HAS_SE 0, WBUF 0) has 36 fp32 adders. Each `otpu_fadd` is roughly
350-450 LUTs and about 190 FFs: an alignment shifter, a 28-bit add, the norm28 shifter and the
rounding. Together they are most of the 23,595 LUTs. Two parts of the design compute more than
they need to:

1. **The lane levels of otpu_vtree use two adders, `u_ln[0..1]`, to do 7 adds per row.** A row
   comes every RL = 8 cycles, so the two adders offer 16 issue slots and use 7. One adder has 8
   slots, which is enough for all 7 adds if they sit in 7 distinct residues mod 8. That is the
   same idea as the accepted "level 2 shares level 1" change. This part also applies to the
   board configuration (SE), which uses the same `g_ln` code.
2. **The long lanes' slot-1 range reduction uses general converters.** `ffloor` builds a 32-bit
   variable shifter and a sticky mask, and `i2f(32'($signed(ii)))` builds a 32-bit negate,
   leading-zero count, normalizing shifter and rounder. They do this for a 9-bit value whose
   magnitude is at most 129. `otpu_se_comp` already does the same step with `rr_floor` and
   `i2f9`, bit-exact over the same domain. There are 2 long lanes (CL = 2).

Timing guard. The worst path family is `m0.imm -> y -> fp_mm -> st[0].v -> lres -> cw_data ->
tw_data[1]` (9 levels, WNS 1.044 ns). It covers the whole top 12 and only goes through long lane
1. MAX/MIN still goes through `st[0].v` and the tap mux in the long lanes. The short lanes
already route it through `lmm`/`lmv` into the last select of `cw_data`. Acceptance needs
fmax >= 154.1 MHz, which leaves only about 33 ps of WNS margin, so placement noise from the area
change could fail the change on its own. Removing this family moves the floor to the next one
(`mi.first -> fbq/R` at 1.143 ns, `xb[0] -> tw_data[6]/R` at 1.169 ns).

## Change

### (1) otpu_vtree.sv, `g_ln` (LN2 only): one adder `u_ln`

Cycle numbers below count from sub 0 on `pacc`. `tr_y` holds the level-2 result of all 8 lanes
at cycle 20. The cycle `c` strobe is `rsr[c - 8]`; let W = DL + LA - 2 (= 12, cycle 20).

| cycle (residue) | load `qa` / `qb` (registered)            | issue                                  |
|-----------------|------------------------------------------|----------------------------------------|
| 20 (4)          | `tr_y[0]`, `tr_y[4]`                     |                                        |
| 21 (5)          | `td1[2]`, `td1[6]` (`tr_y1`)             | L1_0 = x0 + x4                         |
| 22 (6)          | `td2[1]`, `td2[5]` (export `tr_y2`)      | L1_2 = x2 + x6                         |
| 23 (7)          | `t3[3]`, `t3[7]`                         | L1_1 = x1 + x5                         |
| 24 (0)          |                                          | L1_3 = x3 + x7                         |
| 25              | `qa <= xs` (L1_0)                        |                                        |
| 26 (2)          | `ob = xs` direct (L1_2)                  | L2a = L1_0 + L1_2 (= xl[2][0])         |
| 27              | `qa <= xs` (L1_1)                        |                                        |
| 28 (4)          | `ob = xs` direct (L1_3)                  | L2b = L1_1 + L1_3 (= xl[2][1])         |
| 30              | `h <= xs` (L2a)                          |                                        |
| 32              | `qa <= xs` (L2b), `qb <= h`              |                                        |
| 33 (1)          |                                          | L3 = L2b + L2a                         |
| 37              | root = `xs`                              |                                        |

- **Issue slots:** the issue residues are 5, 6, 7, 0, 2, 4, 1. They are all distinct, so the one
  adder is never double-booked across rows that start a multiple of 8 apart.
- **Register loads don't collide:**
  - `qa`/`qb` load L1 operands at residues 4-7, and `qa` loads `xs` at 1, 3 and 0.
  - `h` is written only at residue 6 (cycle 30) and read at cycle 32, before its next write at
    cycle 38.
- **`qa`:**
  - One-hot AND-OR over `{tr_y[0], tr_y1[2], tr_y2[1], t3[3]}`, selected by `rsr[W..W+3]`.
  - Default `xs`.
- **`qb`:**
  - The same mux over lanes 4-7.
  - Default `h`.
- **`ob`:** `(rsr[W+6] | rsr[W+8]) ? xs : qb`. All selects come from flip-flops.
- **New registers:**
  - `t3`: 64 FFs, `tr_y2` of lanes 3 and 7 delayed one more cycle.
  - `h`: 32 FFs.
- **RD:** `RD = ... + (LN2 ? 4 : 0)` (was 2), so 28 -> 30.
- **Lane-level collision check:** becomes `$onehot0` over the 7 issue taps
  `rsr[W+1..W+4], rsr[W+6], rsr[W+8], rsr[W+13]`.
- **Unchanged:** `g_lg` (other LANES) and `g_tp`.

**Bit-exactness.**
- Every add has the same operands and pairings as `xl`: xl[1][k] = x[k] + x[k+4], xl[2][k] =
  xl[1][k] + xl[1][k+2], root = xl[2][0] + xl[2][1].
- Only the a/b order changes, and fp_add is commutative bit for bit, as g_tp already relies on.

**otpu_se_tail.sv.**
- Set `RD_MAX` 28 -> 30 and update its comment.
- T_U does not change. T_U0 goes 90 -> 92, and q_pad gives d = 99 -> o = 13 -> pad 5, so
  T_U = 97 as before and DQ = 104 as before.
- The A/Q window alignment depends only on DQ, so it is untouched.

### (2) otpu_vpu.sv, long lanes' slot 1 pre-stages

Copy `rr_floor` and `i2f9` from otpu_se_comp as local functions of otpu_vpu (do not name any
otpu_fp internals, which trips the sandbox check).

- `t.ii = 9'(ffloor(p0.v))` becomes `t.ii = rr_floor(p0.v)`.
  - p0.v is the clamped v: in [-126, 128), or +0 when lo/hi, including NaN, since
    `!fp_gt(128, NaN)`.
  - It is never subnormal, because it is an adder result or 0.
  - That is exactly rr_floor's domain, and both give floor mod 2^9.
- `t.k2 = i2f(32'($signed(p1.ii)))` becomes `t.k2 = i2f9(p1.ii)`.
  - EXP2: |i| <= 126.
  - LOG2: e = exp - 127 + ge is in [-127, 129].
  - i2f9 is exact for |n| <= 255, and so is i2f, so the two are equal. The sign flip `^ e2` is
    kept.

### (3) otpu_vpu.sv, long lanes' MAX/MIN (timing guard)

As in `g_slane`:
- Drop the `fh[V_MAX], fh[V_MIN]` case from `st[0].v` (default '0; v is never carried).
- Set `lmm[l] = hit[0] && (m0d.fh[V_MAX] || m0d.fh[V_MIN])` and
  `lmv[l] = fp_mm(x, y, m0d.fh[V_MIN])`.

The written value is the same `fp_mm` of the same x and y. It now enters at `cw_data`'s last
select, after the RMAX, root and flush overrides that clear `mm`.

## Expected

| Part | LUT | FF | area_eq |
|------|-----|----|---------|
| (1) | about -370 (one fadd) - 96 (second adder's qa/qb/ob muxes) + 64 (wider 5:1 muxes) = about -400 | about -190 - 64 + 96 (h, t3) + a few = about -155 | about -480 (-1.3%) |
| (2) | about -150 to -250 per long lane, so about -300 to -500 | ~0 | -0.8 to -1.3% |
| (3) | about ±30 | 0 | ~0 |

- **Total:** about -2.0 to -2.5% area_eq, i.e. roughly 37,685 -> 36,800-36,900. DSP 68,
  BRAM18 16 and LUT-RAM unchanged.
- **fmax:** the long lane's MAX/MIN family leaves the top paths, so WNS should rise to about
  1.12-1.15 ns (the `mi.first` fanout and short-lane R-pin families), about 156-157 MHz.
- **New paths:** the new `qa`/`qb` muxes are FF -> 2 LUT -> FF. `ob` stays one LUT in front of
  s1, as today.
- **Perf:** each RSUM/RSSQ/RDOT instruction's last root comes 2 cycles later, once per
  instruction, because rows still stream at one per 8 cycles. That is a few tens of cycles per
  Qwen3 token, far below 0.2%. SE stream timing is unchanged, since T_U is the same.

## Risks

- **(1) is a fixed schedule.** An off-by-one in a strobe tap breaks every RSUM/RSSQ/RDOT and
  DSTEP/STREAM kv.
  - The `$onehot0` check and the bit-exact tests catch this: test_rtl reductions,
    test_dstep_rtl_bit_exact, and test_se_vpu for the shared A/Q tree.
  - Stalls (`en` low) freeze `rsr`, `td`, `t3`, `h` and the adder together, so the schedule holds
    in en-cycles.
- **RD 28 -> 30** adds 2 cycles to every sum reduction. The perf gates (attention_decode >= 0.60,
  the Qwen3 proxy at 0.2%) should not notice. If a kernel is VPU-latency bound per instruction,
  it would show there first.
- **(2)** depends on the domain argument. If some path fed slot 1 a v outside [-126, 128)
  without clamping, the results would differ. The clamp stays in front, and
  test_lane_count_does_not_change_results[4]/[16] exercise the long lanes with EXP2 and LOG2.
- **Whether (2) saves anything:** Vivado may already trim part of the 32-bit i2f/ffloor because
  of the sign-extended input and the 9-bit truncation. Then (2) saves less, and (1) alone is only
  about 1.3%, near the 1% line.
- **(2) and (3) only change the non-SE long lanes.** The board build (HAS_SE) has none, so for the
  board only (1) matters.
- **Placement noise** at the 33 ps fmax margin. (3) is there to absorb it.

## Implementation notes

# Implementation: one lane-level adder, 9-bit converters, long-lane MAX/MIN at lmv

- otpu_vtree.sv (g_ln, LN2 only): the two `u_ln[m]` adders are now one `u_ln`. It follows HYPOTHESIS.md's table, W = DL + LA - 2 = 12. The issue taps are rsr[W+1..W+4] (L1_0, L1_2, L1_1, L1_3), rsr[W+6] (L2a), rsr[W+8] (L2b) and rsr[W+13] (L3). The root is at rsr[29], so RD goes 28 -> 30 (`LN2 ? 4 : 0`).
  - `qa`/`qb` are one-hot AND-ORs over {tr_y, tr_y1, tr_y2, t3}, selected by rsr[W..W+3]; qa's default is xs and qb's is h.
  - `h` loads xs when rsr[W+10] is set. `ob = (rsr[W+6] | rsr[W+8]) ? xs : qb`.
  - New `tr_y2` export (td[2]) and `t3` (lanes 3 and 7, 64 FFs). `xs[0]` is the single adder's output.
  - The collision check is now `$onehot0` over the 7 issue taps (`ln_is`). g_lg and g_tp are unchanged.
- otpu_se_tail.sv: RD_MAX 28 -> 30 (and the DQ comment, 97 -> 99). T_U stays 97 (q_pad 7 -> 5), so DQ stays 104.
- otpu_vpu.sv:
  - `rr_floor` and `i2f9` are copied verbatim from otpu_se_comp as local functions. Slot 1's pre-stages use them in place of `ffloor` / `i2f(32'($signed(..)))`.
  - `rr_floor` matches `ffloor` mod 2^9 for any |x| < 128, subnormals included, because ffloor flushes them first.
  - Long lanes: MAX/MIN is out of `st[0].v`, and `lmm`/`lmv` are driven as in g_slane (no `c_ov` term: long lanes exist only when !C8).
- otpu_se_comp.sv: not changed.
- Checks: verilator lint over RTL_SOURCES + otpu_native_mem is clean (no warnings).
- Tests, all passing:
  - test_rtl: test_mlp_rtl[1], test_lane_count_does_not_change_results[4/16], test_attention_decode_rtl (3), test_fuzz_single_slice[0,1], test_board_memory_path_stress[1-30].
  - test_vops: dstep_rtl_bit_exact + log2_vop (4).
  - test_se_vpu (10).
