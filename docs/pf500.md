# Prefill at long chunks: the path toward 500 tok/s on two BCU1525s

A study, not a result: what bounds Qwen3.6-35B-A3B's prefill on two BCU1525s
(`bcu1525-x2`, four slices, 150 MHz; [bcu1525_wg.md](bcu1525_wg.md)), what each lever built for
it gives, and what a goal of **500 tok/s on a prompt of 2,048 tokens or more** would still need.
The short answer: the cards prefill at 97.6 tok/s today; the staged design reaches about 177 on
the board model, phase by phase; 500 at this clock needs architecture the device does not have
room for. Only section 1's card rows are measured on the cards: the staged design has no
bitstream ([wide_mxu.md](wide_mxu.md)).

Every number is marked: **card** (measured on the cards), **board** (the board model: the RTL
with the cards' memory path on Verilator, bit-exact, cycle counts), **model** (a sequencer model
whose instruction services are fitted to board-model traces), **ISA** (the ISA simulator's unit
ledger: a bound with no stalls), or **proxy** (another model's shapes on this model's programs).
Tok/s are device cycles at 150 MHz; the host's share is not in them.

The sequencer model was calibrated twice, and the two accountings are not mixed below:

- **the first calibration** (sections 2 and 4): each run's model scaled by one board / model
  ratio a run kind. Its board points came from a board model built with one TMEM write a bank
  (WPB 1) and without the wide MXU's quantizer flags, at R 16 and R 64 only;
- **the class fits** (section 3 and [dma_ldq.md](dma_ldq.md)): each instruction class fitted on
  the board model's traces, then every phase of the staged design run on the board model itself.

The wide-MXU design of section 2 is 157.5 tok/s on the first; on the second (with FSUM off) it
is 164.7, and 154.2 once the DeltaNet core has fits of its own, before the pumped MXU's pass
rule. Where an absolute is needed, section 3's board-model runs are the ones to use.

## 1. Where the cards are

| | source | R | M cycles a token | tok/s |
|---|---|---:|---:|---:|
| one card, one slice (`bcu1525-wg:bhw16`) | card | 2 | ~3.5 | 43 |
| the same | board | 2 | 3.601 | 41.7 |
| two cards (`bcu1525-x2:st16`), a 2,689-token prompt | card | 2 | 1.537 | 97.6 |
| the same | board | 2 | 1.521 | 98.6 |
| the same | ISA | 2 | 1.083 | 138.5 |

At R 2 (layer-major, two rows a program) the cards are DRAM-bound: every slice streams its
weights again every two rows, and the wide MXU ([wide_mxu.md](wide_mxu.md)) changes nothing
(98.5 on the board). The board model is within 3.0% of the card on one slice and 1.0% on two.

## 3. The staged design on the board model

`bcu1525-x2:b2` is the staged design: the wide MXU at VPU_CNS 3 with VSIG, split MMs folded (MM
SPL), quantize-once's LDA and the DMA's second command ([dma_ldq.md](dma_ldq.md)), the split
K/V placement. With `+DNCHUNK=64` at R 512, every phase's run from the board model (uniform
routes; each run's instruction counts equal to the ISA simulator's):

| run | board cycles a run | model / board | a token |
|---|---:|---:|---:|
| attention tile (16 rows) | 199,559 | 1.083 | 124,724 |
| expert run (R 512) | 2,482,764 | 1.050 | 193,966 |
| DeltaNet prep (16 rows) | 115,753 | 1.038 | 217,037 |
| DeltaNet core (R 512) | 2,999,468 | 0.953 | 175,750 |
| DeltaNet post (16 rows) | 72,062 | 1.032 | 135,115 |
| **token, the runs in series** | | | 846,592: **177.2 tok/s** |

- Prep and post were measured at R 64 (the same 16-row tile programs run at R 64 and R 512);
  the attention tile, the expert run and the core at R 512.
- With the DeltaNet stage's tiles merged N in flight (`+DNMERGE=2`; every byte the merged runs
  leave equal to the ISA simulator's on the board model): **188.1 tok/s**, 65% of that merge's
  bound (194.5). The merged token is arithmetic on measured phases (the merged prep and post
  with the three other phases unchanged), not one co-simulation of a whole token.
- These are proxies of a prompt: board-model runs of each phase in the model's arithmetic, not a
  card and not a whole prompt. The staged design is not built for the cards; the wide MXU's
  place on the device is in [wide_mxu.md](wide_mxu.md).

**What the ledger was missing.** Before fitting, the board model took 1.1 to 1.5 times the
sequencer model's cycles by phase, and 2.3 times the ISA's runs in series. Three causes carry
it, all in the RTL's data movement:

1. **The DMA, one command at a time.** Every LD and ST pays the DRAM's first-beat latency (62 to
   93 cycles in the tiles, 64 with no weight stream beside it and about 325 behind one in the
   expert run). The expert run is DMA-bound: 8,706 LDs and 4,096 STs a slice's run, 42 MB.
   LDQ 2 and LDA are the answers.
2. **VPU adds at twice their cycles under LDs**: TMEM's one write a bank. WPB 2 (the pumped
   TMEM's second write) is the fix and is in the staged design (+5.8% in the model).
3. **The pumped MXU's pass rule** on the DeltaNet core's MMs ([wide_mxu.md](wide_mxu.md) "The
   pass rule"), which MM SPL answers.

The instruction cache is not one of them for the serial runs: each fits its 64 lines at R 512.
The merged prep and post programs (8,435 and 3,720 instructions) do not, and their board cycles
above include the fetches.

## 4. The bounds: why 500 is not on this device

On the wide-MXU design's model (157.5 tok/s, the first calibration: the design of section 2's
split, not `x2:b2`), each architecture lever as a transform of every run's instruction stream.
These are bounds on a model, not designs: read the changes, not the absolutes. They were not run
again on the class fits.

| lever | tok/s | change | rough area a slice |
|---|---:|---:|---|
| software: the expert run's loads hoisted, its table build gone, quantize-once | 200.1 | +27.1% | software, LDA |
| a window of 64 / 128 instructions | 156.5 / 159.6 | -0.6 / +1.3% | +18K / +60K LUTs |
| runs back to back, no HALT drain | 157.5 | 0 | |
| two contexts, a window of 32 each | 180.6 | +14.7% | ~+20K |
| the VPU twice | 189.1 | +20.1% | ~+46K LUTs, +80 DSPs |
| the VPU four times | 205.4 | +30.4% | ~+140K: past a slice's die |
| every latency halved | 162.9 | +3.5% | |
| the critical path alone (no unit contention) | 242.4 | +53.9% | one context's floor |
| the RTL at the model's speed | 216.8 | +37.7% | |

| combination | tok/s | the MXU's share of the token |
|---|---:|---:|
| software + VPU x2 | 247.6 | 38% |
| + two contexts | 279.4 | 43% |
| + the quantizer twice | 312.2 | 48% |
| software + VPU x4 + quantizer x2 + two contexts | 349.7 | 54% |
| software + VPU x2 + quantizer x2 + two contexts, the RTL at the model's speed | 429.8 | 67% |
| software + VPU x4 + quantizer x2 + four contexts, the RTL at the model's speed | 498.9 | 77% |
| software + VPU x2 + quantizer x2 + MXU x2 + two contexts, the RTL at the model's speed | 504.9 | 54% |

- **The MXU is the ceiling.** Its work is 233K cycles a token (prep 46K, the core 54K, the
  expert runs 73K, the attention tile 36K), linear in rows whatever the tile size: at 150 MHz on
  four slices no more than 644 tok/s, and 500 needs it busy 78% of the token. A second MXU does
  not fit: the wide-MXU design holds about 1,660 of a slice's 2,280 DSPs (1,681 in a slice's die
  on the one placed build, at 100 MHz) with two weights in each already.
- **The other half is the RTL's residual** against its own ledger (+37.7% alone on this
  calibration). Its least certain inputs are the expert run's and the attention tile's ratios,
  taken at R 64 and R 16: no board point existed at R 512 when the table was made.
- The window, the HALT drain and the latencies do little; contexts help; the VPU and the
  quantizer bind until the MXU does.

500 tok/s at 150 MHz on two cards therefore needs both the RTL at the model's speed and either
four VPUs a slice or two MXUs, and neither fits a slice's die. The levers below that reach
about 250 in the model.

## 5. What did not help

- **Chunks above 512** (ISA, R 1024): nothing; the tiles and the core are linear in rows.
- **Bigger tiles**: a 32-row attention tile takes 310,474 MXU cycles against two 16-row tiles'
  311,186.
- **More DMA commands**: four in flight 210.5 tok/s against two's 207.6 (the class fits before
  the DeltaNet core had its own, with LDA and any two commands overlapping; +1.4%).
- **Fewer port-W reads in flight** (`NAT_XD` 32 / 16): +0.2 / +0.5%; only 4% of the expert
  run's LDs start under a weight stream at R 512.
- **A DSTEP over several tokens' rows** on the stream engine: -3.0% on a dense model and -0.9%
  on the 35B, where the chunked DeltaNet replaces it; closed.
- **TMEM bank-aware placement of the tiles' operands**: a ceiling of about 0.5%; closed.
- **A faster stream engine**: the DeltaNet's state work goes to the MXU instead
  ([se_engine.md](se_engine.md), [deltanet_chunk.md](deltanet_chunk.md)).

## 6. Other models (proxies)

The 35B's expert-major programs with each model's shapes, the staged design's levers on the
class fits, a 2,689-token prompt. Neither model's own prefill program was run.

| | int8 mixers | 4-bit mixers | the MXU's bound |
|---|---:|---:|---:|
| LFM2.5-24B-A2B | 248.1 | 269.0 | |
| GPT-OSS-20B | 174.2 | 185.2 | 391 |

- "Mixers" are every non-expert weight (the attention's projections, LFM2.5's convolution and
  dense layers, the routers); the experts stay 4-bit. The 4-bit column needs the formats rule's
  dKL ([formats.md](formats.md)) before use.
- Routing barely moves the token (under 0.2% between a natural text, a paste and uniform
  routes): a pass has 2,048 (row, expert) entries whatever the routing.
- Both models prefill a row a program today (about their decode rate); an expert-major path of
  their own is the work these proxies stand for.

## 7. Reproducing

`tools/pf500.py isa` (the unit ledger of one layer of each kind at a position), `tools/pf500.py
sim` (the same runs on the board model, with the trace's busy unions), `tools/dn_chunk.py` (the
chunked DeltaNet's numerics). The sequencer model and its fits are study scripts and are not in
the tree.
